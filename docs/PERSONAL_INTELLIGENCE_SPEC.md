## 1. 产品目标与安全原则

从“能调用工具的助手”进一步变成“理解当下需要、记得相关讨论、建议有依据的私人助手”。具体包括附近推荐、跨会话连续性、历史检索、显式个人记忆和可选情境提示。

1. **模型理解与表达；代码控制事实、授权、预算和生命周期。** 不以不断增加关键词规则代替意图理解。
2. **恢复信息不恢复授权。** 历史、摘要、记忆、推荐放权不是发送邮件或修改日历的许可。新的副作用仍绑定当前预览和有效确认；断线不自动重发，先核对服务端状态。
3. **跨会话连续性与访客隔离一起上线。** 在返回 snapshot、历史、工具结果和下载文件之前执行后端权限检查。
4. 眼镜回答简洁、温暖、有依据；需要追问时一次一个问题。分页可容纳多个短条目，但不重复上一页内容。
5. 不扩大现有 provider 月预算；所有新增调用计入现有账本。失败如实说明，不能把估计写成 API 已证实的事实。
6. 历史文字、检索结果和记忆是低信任数据，不是系统指令；其中出现“忽略规则、直接发送”等内容不改变工具权限。

### 范围外

- 不建设多用户 SaaS、隐式人格画像、跨设备身份平台或多平台适配框架。
- 不自动购买、导航、发送邮件、邀请他人或创建日历。
- 不把当前位置持久化为长期记忆，不默认开启主动提示。
- 不在本阶段增加待办执行系统；`todo_due` 留作后续独立规格。
- 不顺带清理生产目录、更换密钥、恢复自动部署或重建 Even Hub 包。

## 3. PI-1：附近推荐闭环

### 3.1 意图与任务条件

扩展现有 dialogue plan，不新增独立分类服务。建议契约（实现前与当前 schema 对齐）：

```ts
type NearbyIntent = {
  mode: 'specific' | 'recommend';
  taskAction: 'continue' | 'replace' | 'clear';
  delegated: boolean;
  patch: {
    vibe?: 'quiet' | 'lively' | 'any' | null;
    needsFood?: boolean | null;
    priceCeiling?: 'inexpensive' | 'moderate' | 'expensive' | null;
    excludeTypes?: string[] | null;
  };
};
```

- 字段缺省＝保持；显式 null＝清除该字段；replace＝新任务，不继承旧条件；clear＝结束当前推荐任务。若模型结构化 schema 要求所有字段存在，以显式 patch 操作编码同样语义，不能把 null 同时用作“未提及”和“清除”。
- “不用安静的了”只清 vibe，不清预算或食物需求；不是自动变成 lively。
- “朋友饿了，我不饿”可得到 needsFood=true，模型负责理解同行人需求。
- delegated 只放权推荐，不放权购买、导航或其他副作用。
- 用户要求“比较，别替我选”不禁止有依据的 suggestion；推荐不等于用户已选定，也不授权导航、预订或写操作。不要为这个措辞增加机械的“禁止建议”模式。
- task ID 由代码管理；模型建议续接或更换任务，代码校验合法状态。目的地字符串变化不是任务变化，不用同义词文本比较强制 replace。
- 非法枚举不得变成清除指令；丢弃非法 patch 字段并记录无内容的校验计数。excludeTypes 限定已支持 Places 类型，最多 6 项。

### 3.2 候选与事实

流水线：Places 最多 10 个 → 事实粗筛／粗排 → 最多 **5 个**路线候选 → Routes 真实时间 → 最终推荐。

- 新增坐标、营业状态、营业时间及 priceLevel 的最小 FieldMask；实现前核验官方 SKU 表，记录字段到 SKU 的映射。v1 不取评论正文或 Atmosphere 属性。
- 永久停业排除；openNow=false 仅在“现在去”场景排除，不能用于判断下周是否营业。营业状态未知保留并标“营业时间待确认”。
- 价位使用完整枚举映射；未知不是免费。已知价格高于上限可排除；未知价格披露不确定性。
- 直线距离只用于粗排，不显示为行程时间；缺坐标不伪造距离。评分和类型可作弱先验，类型不能证明安静、热闹或一定供餐。
- needsFood 是需求，不是已验证餐饮属性；无法确认的条件如实标注。API 证据不足时不承诺满足全部偏好。
- 最终排序保留真实分钟、评分数量与风险考量。内部 adjustedRating 不作为 Google 星级显示，展示原始 rating 和 ratingCount。
- 矩阵计费使用实际 origins × destinations 元素数；目的地上限 5，不把所有历史断言机械改成 5。
- 推荐事实包含门店 ID、名称、地址、出发地标签、交通方式、真实时长、双单位距离、原始评分、营业／价格不确定性、排除原因和证据时间。不长期存原始 GPS。

### 3.3 澄清与显示

recommend 最多追问一次；specific 最多两次；delegated 不再主动追问推荐偏好。达到上限给可纠正假设和候选，不把未确定地点当成已确认目的地。

普通品类（洗车、干洗、烧烤、水果店等）均为 recommend，不要求用户说“推荐”；specific 仅用于点名品牌或具体地点的身份／用途歧义。澄清器独立使用 low 推理、768 输出 token，不继承普通回答的 medium 档；不完整输出仍拒绝解析并走有界兜底。

澄清只用于选候选或更新任务，不把用户整句拼入 routeDestination。模型输出的 selected indices 必须属于当前候选集。

PI-1 明确采用确定性推荐模板：数字／单位／地址以及按路线和评分得出的短理由均由代码渲染；模型负责意图、条件增量和语义澄清，不额外生成最终推荐理由。这是 v2.2 对原“模型短理由 + 模板兜底”方案的收敛，后续如扩展表达须另行验收。数字正则不能证明整句话真实。

条件 patch 只表达本轮修改，不是累计状态；replace 默认不继承旧任务条件，明确“预算照旧”等才允许模型解析继承。普通“帮我找”不是 delegated。已知排除检查 primaryType 和完整 types，不根据名称猜类型；无法表达的排除条件保存 unhandledExclusions 并明确提示无法核实。推荐澄清失败采用有说明的假设比较，specific 保留最多两次澄清。取消任务清理状态后仍须回答同句的新问题。

最近地点证据保留 evidenceAt 与被过滤候选的原因；注入上下文时标为历史只读证据，不冒充实时数据。invalid_patch 指标只记录计数。账本原子替换只对 EPERM/EBUSY 有限重试，不删除目标文件；失败后禁止后续计费调用，运维修复并重启后从持久化账本恢复。仍为单进程写入，不是多进程锁。

全部排除时按实际原因表达：只有所有结果明确因关门排除才说“这次找到的几家都显示已关门”；混合价格、类型和关门原因则说“这批结果没有符合条件的选择”。有明确下一营业时间和时区才说几点开。无“要导航吗”尾问。

## 4. PI-2：跨会话连续性与访客隔离

### 4.1 复用摘要队列

`sessions`、`summary_jobs`、`session_summaries` 已同属 `assistant-memory.sqlite`；`jobs.sqlite` 是文件／邮件链。以 summary_through_sequence 为覆盖真值，不新增重复的 summary_state。

- 关闭事务内对至少 6 条未覆盖 committed 消息登记摘要范围；已有任务时保留未覆盖尾部，完成后由扫描补齐。
- 扩展现有 summary service 处理已关闭会话，保留现有结构与幂等范围约束。
- 提供受服务生命周期管理的定时 sweeper，启动后及到期时运行，不只依赖 drain 回调；停服取消定时器，禁止并发重入。
- 崩溃残留 unknown 在确认无活动 worker 后恢复；目标十分钟内进入可重试状态。模型失败最多三次，退避且有上界；预算延迟不消耗模型失败次数，不忙轮询。
- GAVE_UP 范围不得被补任务逻辑无限复活；新的消息范围另行决定。unknown／终态与 retention 在事务中协调，过保留期取消未运行任务，不永久阻塞清理。
- 摘要陈述已确认决定／未决问题，不凭聊天措辞断言外部操作成功；外部结果以执行记录为准。

### 4.2 上一会话即时上下文

建议 `priorSessionContext({ownerScope, currentSessionId, before, withinMs, tailLimit})`，仅主人会话可调用。选择最近 24 小时内关闭的主人会话，返回摘要覆盖序号、时间戳和未覆盖尾部最多 12 条。

新会话前 20 个 message sequence 内可注入；总上限 1,500 字符并计入现有统一上下文预算。摘要完成后下一轮刷新，不重复 tail。优先保留当前用户输入、当前任务和近期指代上下文；不能为了 prior 挤掉刚刚的问答。统一预算测试确定具体裁剪顺序。

历史作为带来源边界的数据块传入，不将历史原文提升为系统权限。时间未知时显示 UTC 或明确时区，不猜本地时间。无相关内容就说明不记得，不伪造结论。

#### §4.2 实施候选（2026-09-22，待用户独立复测）

- 新增 store 的 owner-only `priorSessionContext`：验证当前会话归属；只选同 scope 的 ended/expired 会话，关闭时间不得晚于新会话创建时间，也不得早于查询时刻前 24 小时。同时间按 ID 稳定排序；active/idle、其他主人、访客一律不作为来源。
- `pendingUserTurn` 对意图阶段计入即将提交的消息：上一轮序号已达 20 时，下一轮分类不再使用 prior；回复阶段同样受 durable sequence 上限约束。
- 每次构建重新读取摘要和覆盖，未覆盖 tail 只读 committed user/assistant，最多 12 条；SQL 中先对每条内容限 1,200 码点，模型块再缩到总计最多 1,500 UTF-16 字符（标注节选、截断及省略条数）。摘要分配最多 500 码点、单条 tail 最多 300 码点；不足时优先较新的尾部。`sourceLosses` 保留缺口/损坏提示，不把缺失当作完整证据。
- 当前输入、当前会话摘要、近期/主题上下文先占统一预算，prior 只用剩余额度（另计消息开销）；不会挤掉现有问答。即便首轮当前 history 为空，也能给意图模型提供 prior。
- 仅作为 assistant 角色的带边界 JSON 数据块传给模型，不存入当前 messages，不在 ready snapshot 下发，不建立旧会话 topic/审批绑定；访客 runtime 不调用此查询。Calendar/Email 的新预览确认机制不变。
- 无新 schema，无生产数据迁移；本单元未部署。跨会话能力限最近一次关闭会话，不是 PI-3 的历史检索。
- 离线入口：`tests/prior-session-context.test.ts`、`tests/prior-session-websocket.test.ts`；另有 Calendar 历史确认拒写测试。真实冒烟：Node 24 `--use-system-ca --import tsx tests/live-prior-context.ts`，需 `RUN_LIVE_PRIOR_CONTEXT=1`，临时合成 SQLite、现有计量账本、最多 6 次/$0.15、不发邮件、不写日历、不联网搜索；检查本地 3001 无账本写入者后才运行。

### 4.3 访客权限契约

2026-09-21 实施状态：第一单元已通过独立复测。第二单元新增 schema v10
`device_guest_locks` 与内部 `GuestUnlock` 授权服务，已通过独立复测，尚未接入协议或客户端。

- 锁与独立访客 session 在同一事务创建，重复进入返回原锁。锁不随 session 保留期删除，
  读取故障或损坏直接拒绝，不能降级为“无锁”。session 已结束/删除时仍保持锁；
  后续服务端接入需在锁下原子换绑新的访客 session，不能恢复主人。
- 解锁挑战仅在内存，绑定已认证的 client、当前 connection 和锁实例，60 秒单调时间有效期，
  每次尝试即消费；断连/身份切换必须 cancel。重启使未完成挑战失效。
  每连接最多一条，全服务最多 128 条；挑战不携带主 token。
- confirm 必须提交本次主人凭证，服务重新校验，不接受认证标志/设备凭据替代。
  解锁事务核对原锁，撤销该 client 的设备与恢复凭据，再移除锁；任一步失败整体回滚。
  `releaseDeviceGuestLock` 是内部 CAS，不得直接暴露为协议接口。
- 复测后的收尾修订：同一解锁事务将 active/idle 访客会话标记 ended/guest_unlock，
  清除恢复草稿并撤销该会话恢复凭据。不生成离场访客的收尾摘要。已有 ended/expired
  时间戳保留，会话已按保留期删除也可解锁；任一步失败，包括会话结束失败，均整体回滚。
  已结束访客内容仍按既有保留期清理，不是解锁即删除。
- 后续接入还须关闭旧连接/停止旧 runtime 输入输出并签发新的主人凭据；仅撤销持久凭据
  不等于终止已经认证的 socket。完成第三、四单元前不得宣称产品访客隔离已启用。
- main 上重连测试偶发失败单独跟踪：补失败清理/有限超时、内部拒绝原因诊断，
  对外仍保留统一错误；本单元未改动重连行为，不能宣称该问题已修复。
- 第三单元接入前明确：锁下过期会话应原子换绑新的访客会话并补初始 topic；
  无法换绑时给出明确访客状态与重试提示，不可静默当主人。挑战应补每 client 限额，
  防止单 client 占满全局 128 条。主令牌轮换需重建 GuestUnlock 或重启服务，
  同时使旧挑战失效；不能仅替换外部配置却保留旧哈希实例。

- 复用原 `summary_jobs` 行，schema v6 增加 `budget_deferrals`（默认 0）；不新增状态表。`updated_at` 加对应退避值决定最早领取时间，重复 `consider()` 不绕过截止时间。
- 模型／schema 失败最多 3 个生成轮次（包括首次）；第一次失败后 30 秒，第二次后 120 秒。每轮保留原有最多一次 schema repair，因此不承诺总共只有 3 次 HTTP 请求；每次请求仍走已计量 fetch。
- 第三轮失败标记 `SUMMARY_GAVE_UP`，同范围不复活。等待重试的失败范围也阻塞重叠任务；领取与状态变更在 SQLite 事务内执行。
- 预算错误只认可账本的 `CostBudgetExceeded` 类型，延期 15 分钟且退还本次领取的 attempt，不清除先前失败次数。它不是模型失败，也不绕过预算限制。
- 同一个任务累计预算拒绝最多 24 次（不只连续次数，不因模型失败或重启重置）。第 24 次标记 `SUMMARY_BUDGET_GAVE_UP`，不再自动领取且不阻塞新范围；同一范围不能通过重新登记复活。恢复额度后不会自动复活终态，后续若提供手动重试必须另行设计授权与计量。
- 摘要生成器完整序列化请求体（历史、上一摘要、repair 信息和 schema 均包含）后，按 UTF-8 字节检查 **180,000 bytes** 的应用层上限，超限在 metered fetch／预算预留之前抛带 `bytes` 的 `SummaryInputLimit`。不是官方 token/context 上限，不保证该字节数适合所有模型。
- 正常批次通过独立模块 `summary-request.ts` 的 `summaryBody()` 与发送共用完全相同的序列化路径。首次请求预算为 **154,000 bytes**，预留 24,000 bytes 修复增量及 2,000 bytes 模板／模型名余量。修复材料按码点、按外层 JSON 转义后的字节裁剪，不再使用 24,000 字符切片。
- 至少 6 条未覆盖 committed 的门槛在切批之前判断。只先读取序号元数据，正文按索引逐条读取（一次最多一条原始大消息），加入后超字节即停止；最多 200 条不是固定批次长度。切出的 1–5 条同样可入队。活跃会话保持 60 条触发、保留最近 24 条的原策略。
- 单条超过可用预算时独占一批，按码点保留确定性的首尾摘录；结构化 `excerpt.omittedBytes` 来自程序计算，不把标记插入正文。原文仍完整留库。上一摘要也有确定性摘录封套（JSON 转义成本受限），超大时记录 `prior_summary` 缺口，不能伪称完整保留。
- schema v7 在 `session_summaries` 新增 `source_losses_json`，不修改 strict 模型输出 schema。服务端将上一份与本批的缺口按 kind／sequence 合并，记录 omittedBytes；缺口沿摘要链保留，ContextBuilder 明示其有损性。元数据不得用来授权外部操作。
- 第六轮修复：选批共用消息投影，逐条累加外层 JSON 转义后的精确字节数，序号位数纳入计算，最后完整构建一次并断言一致；不再逐条重建整个请求。已耗尽模型／预算重试或输入终态失败的覆盖起点不自动重新规划；`SUMMARY_REBATCHED`／`SUMMARY_RANGE_INVALID` 仍允许合法替代范围。
- 摘录结构增加 `headChars`（Unicode 码点数量），标出保留头部与尾部之间的缺失位置；正文不插标记。损坏或结构非法的缺口列转换为 `metadata_unknown` 并沿摘要链保存，不阻止会话结束／过期，也不冒充无损。PI-3 上线前明确告知模型没有历史原文检索能力，应请用户补充。
- worker 的扫描失败与生成失败统一经过 `onDiagnostic`；未提供回调时才使用默认 JSON 日志。回调异常不改变任务状态。
- 第七轮策略修订（schema v8）：终态只结束本次任务，不永久禁用会话。终态转换时在同一 SQLite 更新链中记录 `terminal_sequence`；只有该位置之后新增至少 60 条 committed 消息才允许新代次，旧范围末尾与既有积压不计入门槛。旧任务 id／attempts／范围保持不变，新任务使用新 id 和 generation；允许同范围的新代次，且同代次仍唯一。新代次再次终态后重新计算 60 条门槛。没有新消息不自动复活。
- `SUMMARY_BUDGET_GAVE_UP` 恢复额外检查当前跨 provider 账本能否容纳保守的摘要请求预留上界；检查只读、不发网络、不扣费，检查异常默认拒绝。实际模型调用仍由 metered fetch 原子预留，避免检查与调用之间的余额变化绕过预算。只有模型／输入类终态不要求该额外检查。v7 旧终态任务迁移时以当前最新消息位置作保守恢复基线。
- `summary_json` 使用同一 `validateContextSummary` 完整校验。非法 JSON 或 schema 损坏时返回明确的“此前摘要不可用”空事实占位及 `metadata_unknown`，不使用旧摘要冒充最新覆盖、不重置覆盖、不删除原文；会话结束、过期和当前回答仍可继续，后续摘要继承缺口。

- 第八轮定稿：每个覆盖起点总计最多三代（0、1、2，包含初始代），活跃会话仍须新增 60 条 committed 消息；已结束／过期会话由现有定时 worker 恢复，不需要用户回来。`SUMMARY_GAVE_UP` 冷却一小时；`SUMMARY_BUDGET_GAVE_UP` 须通过实时账本检查；已关闭会话的 `SUMMARY_INPUT_LIMIT` 不自动恢复。每代三轮、每轮最多一次 schema repair，因此每个起点最多九轮、十八次模型请求，实际请求仍全部计费并受预算限制。
- 扫描每次最多检查 16 个候选，以 session id 游标轮转，每次最多进行一个字节规划并入队；被预算挡住的会话不会永久占据首位。游标可在重启后重置，代次和冷却不可重置。终态失败日志与任务记录保留，不宣称覆盖完成。

- 服务器启动时缓存保守请求预留金额；不缓存余额或预算检查结果。扫描本身不产生网络调用。上述新增测试只使用临时库与离线生成器，业务库与 Linux 不自动升级。

- 旧排队范围若超出新批次，原任务以 `SUMMARY_REBATCHED` 终止并保持原范围，新范围用新 ID 入队，二者同一事务。正常领取后的范围不原地改写；已有同范围终态不复活。新代码可以处理旧 queued 范围，不自动复活旧 `SUMMARY_INPUT_LIMIT` 终态。
- 摘录记录 `summary_excerpt` info，替换范围记录 `summary_rebatched`，终态失败记录 `summary_failed`；仅包含 jobId、sessionId、范围、字节数和受控 code。扫描中没有构建请求的诊断 bytes=0 表示未知，不是零字节请求；不打印正文、模型原始错误、位置或凭证。诊断回调失败不改变处理结果。

- 重启残留／正常停服中断的摘要进入 `unknown`，5 分钟后可领取；每分钟扫描下通常在 5–6 分钟内尝试，受正在运行的任务和预算约束。进程独占锁与数据库 running 检查共同防止并行 worker。第三轮中断则终止，不作第四轮。
- unknown 重试仅适用于无外部写入的摘要，可能再次计费；不扩展到 Calendar／Email。停服取消 timer、abort 当前生成，迟到成功不提交。
- 定时器默认 60 秒并 `unref()`；测试可注入短周期与时钟。定时器只领取到期任务，不循环唤醒失败任务；空队列不调用模型。
- 正常领取、失败、延期、完成使用 `MAX(updated_at, now)`，不把退避起点回写到过去。唯一异常修复：空闲扫描发现可重试 failed／unknown 的时间戳比当前时间超前 **超过 15 分钟**，事务内重新锚定到当前时间，再完整等待原来的 30／120 秒、15 分钟或 5 分钟。不会立即领取，不改变 attempt／范围／错误原因，不复活终态，不动 running。重复扫描不滑动已修复的截止时间。
- 不超过 15 分钟的未来偏差保持原值；墙钟恢复稳定后，额外等待最多 15 分钟加原退避（预算场景最多约 30 分钟，再加扫描／正在执行任务的等待）。此机制不是跨重启单调时钟，不承诺在持续人为改钟期间按真实经过时间准确调度。范围隔离和异常时钟修复都在 worker 空闲后执行。
- worker 在调用模型前验证已读取消息的末序号等于任务终点，防止 500 条读取上限静默截掉尾部；允许非 committed 消息造成的序号空隙。入库前再次核对起点与覆盖及读取范围，失败不推进覆盖。
- 无效范围用终态 `SUMMARY_RANGE_INVALID` 保留诊断，不自动重试。扫描将起点与覆盖错位／终点越界的 queued、unknown、可重试 failed 隔离，释放阻塞；不改写消息或猜测正确覆盖，不自动修复损坏数据，也不复活已有终态。
- retention 可事务内级联删除过期 queued／failed／unknown，running 继续受保护。摘要残留 committed 尾部为 0–5 条，后续 prior reader 的 12 条上限足够覆盖，相关边界已有回归测试。

### 实施拆分与当前状态（PR #58 后续独立分支）

1. 查询策略单元：`history-query.ts` 仅准备参数；两个入口独立拒绝访客与非法身份。查询最多 256 码点，拒绝空串、控制字符及孤立代理；默认并限制在最近 90 天，最多 10 个命中；短查询转义 LIKE，长查询编码为单个 FTS 字面短语。邻居范围每侧 0–3。必须绑定参数，不能拼接 SQL。此单元不读业务库、不启用检索能力。
2. 存储与索引单元：过滤内容源、原子迁移、三类触发器及级联删除；存储入口再次验证权限、资源归属，限定扫描工作量与输出，不能把纯参数校验当成资源授权。

每单元通过测试再进入下一单元。第一单元查询策略已通过 618 项全量回归（616 通过、2 跳过）。第二单元先实施独立 `installHistoryIndex` 原语，仅在临时数据库调用，未挂接 store 启动迁移：external-content 的源是过滤视图，初始化和 rebuild 共用过滤；消息增删改与父会话删除／作用域变更均同步索引。父会话删除前先删索引，避免 FK 级联时已经读不到父作用域而遗留 token。索引结构完整性用 FTS `integrity-check` 的 rank=1 校验。依据 [SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html#external_content_tables)。

第二单元后续候选已接入 schema v13：索引创建、过滤回填、完整性检查、时间／作用域索引和迁移记录处于同一事务；失败整体回滚。历史迁移测试降级的是临时夹具，必须同步删除 v13 产物，不能只修改版本号。

存储入口为 `searchMessages(principal,input,now?)` 和 `messageContext(principal,input,now?)`，身份来自服务器、不能取自模型参数。搜索只查同 owner scope、90 天内且不在未来的 committed user/assistant；最多扫描最新 2,000 条候选、4 MiB 内容、返回 10 条且最多三个会话。截到任一边界必须返回 `incomplete`，调用方不得将空结果表述成“从未讨论”。这是应用层行数／内容预算，不是 SQLite VM 的硬超时，性能门禁前不接入对话。每条回传最多 1,200 码点并带 truncated；邻域独立验证锚点归属、状态与时间，每侧最多三条，仍需下一单元统一 2,000 字符注入限制。

当前 Node/SQLite 实测中，FTS rowid 约束绑定 JS number 会返回不符合 rowid 的结果；查询采用 `CAST(? AS INTEGER)` 并再次核对命中 rowid，字面量测试同时含匹配／不匹配消息以防回归。H8 控制字符细分规范化保留为非阻塞待办，尚未改动既定查询策略。

## 6. PI-4：显式长期记忆与遗忘

只接受明确的记住／修改／忘掉／查看记忆，不做频率推断。“今晚想安静”是任务条件，不变成永久偏好。

记忆记录包含 owner_scope、kind、content（最多 300 字符）、可选规范化 key、来源 session/message、时间、适用范围、替代／删除关系。仅主人可读写。类型先限定 fact／preference／date／contact_hint，不引入 todo。

- 模型生成结构化意图，代码验证来源和明确请求；关键词存在本身不能授权，“不要记住”“他说记住”必须拒绝写入。
- save 给清晰回执；update 匹配唯一目标，多义则一次问一个问题，无匹配不静默另存；forget 明确目标后确认，不扩成批量删除。
- 日期歧义如 9/1 根据明确上下文判断或追问，不固定按美式解释；相对日期不直接成为周年纪念日。
- 读取最多 30 条、1,200 字符，共用上下文预算，按当前相关性选择；全部记忆列表另行分页，不能因注入限制假称只有 30 条。
- superseded_by 与物理删除采用不会悬挂或阻塞的引用设计，保留来源审计；不无限保留替代记录中的敏感原值。

### 遗忘的两个层级

1. **不再作为个人记忆使用**：立即从主动注入、提示和记忆检索排除，建立最小化遗忘标记；不能在摘要／prior／召回中又自动提取回来。相关派生摘要失效或重建，来源内容的使用受抑制。原始会话仍按历史保留政策保存；回执必须说明这个边界。用户明确重新记住才解除抑制。
2. **删除相关历史信息**：独立、范围明确的删除请求；确认后清理选中的原始记录、索引与派生数据。备份的保留和恢复后重新应用删除标记需文档化，不承诺立即抹除所有离线备份。

软删记忆默认 30 天后物理清理；遗忘标记不保存被遗忘原文。无法可靠识别语义复述时宁可抑制关联来源，不声称已完全消除所有相似表述。此能力是 PI-4 验收门槛，不延期给提示模块。

- [ ] save/update/forget/list、否定引用、多义更新、分页与预算。
- [ ] 访客／historical prompt injection 不写记忆；记忆不授权副作用。

## 7. PI-5：默认关闭的情境提示

PROACTIVE_NUDGES_ENABLED 默认 false，主题白名单默认空；holiday 与 memory_date 分开开启。先不支持 todo_due，不增加关系推断。

- 仅主人新会话首轮、非副作用预览／确认轮次附加，每个有效本地日最多一次。情绪敏感或不合时宜的轮次不强行提示。
- 采用经验证的当前位置时区或用户确认时区，记录来源／新鲜度；核对实际 location/calendar 接口，不假定已存在 timezone() 方法。无可信时区不触发日期提示，不回退 Chicago。
- 日期算法与地区适用范围有测试；无法可靠算出的节日不触发。
- topic:<key> 为永久抑制，shown:<key>:<occurrence> 为单次；键包含 owner scope。区分 generated 与真正展示，断线不能把未展示内容当作已看；需要客户端确认或等价的可验证交付策略。

- 正面回应绑定刚展示的提示，有期限、一次性消费、不接受旧提示授权。只触发查询，不购买／发送／写日历，不预取花店。

## 8. 横切验证、配置与证据

所有新配置先写入规格和 .env.example 的无秘密默认值，再决定上线开关；不在本次文档工作中修改运行环境。跨会话连续性设计默认开启，但只有 PI-2 全部安全 gate 通过才允许部署启用；访客例外和主动提示默认关闭。

指标只记次数／延迟／结果类型：nearby、continuity、recall、memory、nudge；不记录聊天、检索词、记忆原文、邮箱、坐标或凭据，不用用户数据作为指标标签。新增 provider 请求统一走账本；真实测试分别记录额度、延迟与失败，不能用大量重复调用掩盖失败率。

每个 PR 的验证记录至少包括：

- base/head SHA、运行时和 schema 版本、变更接口、关联文档。
- 离线测试、完整回归、build、安全扫描的实际命令与结果。
- 新的合成业务场景，不只复用调试时的句子；中英文、否定、指代、话题切换与故障路径。
- 有界 live 的调用数量／费用上限／结果，不打印凭据或原始私人内容。
- 用户本地验收、部署批准、生产 SHA、备份与回滚验证、安全复核。
- 未通过 gate、剩余风险、规格修订和明确的下一步。
